# Security Model

Платформа строится по принципу **«нулевого доверия» (zero trust)**: любой агент и любой инструмент считаются потенциально недоверенными.

## Уровни защиты

1. **Identity & Access Management.** SSO (OIDC/OAuth2), сервисные аккаунты, ротация секретов.
2. **MCP Gateway.** Единая точка авторизации для всех вызовов внешних инструментов. См. [mcp-gateway.md](modules/mcp-gateway.md).
3. **RBAC per agent.** Каждой роли — минимально необходимые права (capability‑based access).
4. **Sandbox isolation.** Каждый агент в собственном контейнере / microVM. См. [sandbox.md](modules/sandbox.md).
5. **Command policy.** Чёрный список опасных паттернов; ручное одобрение для подозрительных команд.
6. **Network egress control.** Per‑container firewall / прокси.
7. **Secrets isolation.** Секреты — только через secret store (Vault). Никогда не в `state` и не в логах.
8. **Audit log.** Все действия и обновления `state` пишутся в неизменяемый журнал.
9. **Session isolation.** Данные одной сессии недоступны другой.
10. **Data filtering.** Входы/выходы фильтруются на PII перед отправкой во внешние LLM.

## Trust boundaries

```
┌──────────────────────────────────────────────────────────────┐
│  Trusted plane: Orchestrator · Planner · Validator · Reflector│
└──────────────────────────────────────────────────────────────┘
                │  authenticated calls
                ▼
┌──────────────────────────────────────────────────────────────┐
│   Worker Agents (semi‑trusted, in sandbox, role‑scoped)      │
└──────────────────────────────────────────────────────────────┘
                │  MCP Gateway (RBAC + audit)
                ▼
┌──────────────────────────────────────────────────────────────┐
│        External Tools / DBs / RAG / Internal services        │
└──────────────────────────────────────────────────────────────┘
```

## Sandbox: сравнение технологий

| Технология | Пример | Изоляция | Оверхед | Когда использовать |
|------------|--------|----------|---------|--------------------|
| Docker | Стандартные контейнеры | средняя | низкий | Базовый кейс, дешёвые агенты. |
| gVisor | Google gVisor | высокая | низкий–средний | Дополнительный слой над Docker. |
| Kata / Firecracker | Kata Containers | высокая | средний | Чувствительные агенты, code‑exec, ненадёжный input. |
| KVM (full VM) | Традиц. VM | очень высокая | высокий | Особо чувствительные сценарии. |

В дефолтном профиле:
- **обычные агенты** — Docker + gVisor,
- **агенты, исполняющие сгенерированный код** — Firecracker / Kata,
- **agentless tasks** (только LLM) — без отдельного контейнера, но всё равно через RBAC.

## Command policy

Команды (особенно `bash`) пропускаются через политику:

1. **Hard blacklist** (запрещено всегда):
   `rm -rf /`, `:(){:|:&};:`, `mkfs`, `dd of=/dev/...`, обращения к `/proc/self/mem`, и т.д.
2. **Suspicious greylist** — требуется явное одобрение пользователя или LLM‑judge:
   сетевые операции к произвольным адресам, изменение системных файлов, скачивание исполняемых файлов.
3. **Whitelist** — допускается без подтверждения внутри текущей роли.

В режиме `auto-approve` (`/yolo`) проверки могут быть ослаблены — но только по явной команде пользователя и с пометкой в audit‑логе.

## Secrets

- Хранение: HashiCorp Vault / AWS Secrets Manager / Cloud KMS.
- Доступ: токены коротко живущие (TTL ≤ 15 минут), скоупом до конкретного инструмента.
- В контейнерах секреты **не присутствуют как переменные окружения**, а резолвятся через MCP Gateway по запросу.
- Логи проходят через redaction‑фильтр.

## Аудит

- Все вызовы MCP, обновления `state`, человеческие одобрения и системные команды → структурированный `audit_event` с `trace_id` и `session_id`.
- Хранение в WORM‑бакете (immutable storage) либо в append‑only журнале.
- Регулярные отчёты для compliance / SOC2 / GDPR.

## Data flow controls

- **PII guard.** Перед отправкой во внешние LLM применяется PII‑detector + redaction.
- **Output filter.** Ответы LLM проверяются на secret leakage и токсичность.
- **Egress allowlist.** Контейнеры могут общаться только с разрешёнными внешними доменами.

## Threat model (кратко)

| Угроза | Митигатор |
|--------|----------|
| Prompt injection / jailbreak | LLM‑judge, output filter, ограниченные tools, command policy. |
| RCE через сгенерированный код | Sandbox с network‑off, FS‑readonly, ограниченный CPU/RAM, kill‑switch. |
| Утечка PII во внешнее LLM | PII guard, redaction, локальные LLM для PII‑sensitive шагов. |
| Несанкционированный доступ к данным | RBAC в MCP Gateway, capability tokens, аудит. |
| Атака на supply chain | Pin версий, SBOM, проверка сигнатур образов, scoped deploy keys. |
| Боковые движения между сессиями | Session isolation, отдельные namespace и FS. |
| Боковая атака через общую базу/ключ | Per‑tenant ключи, отдельные DB‑роли с ограниченными правами. |

## Соответствие нормативке

- Архитектура совместима с GDPR (право на удаление, audit trail).
- Поддерживается **data residency** — выбор региона для хранения и обработки.
- Все внешние LLM‑вызовы могут быть ограничены белым списком моделей / провайдеров согласно политике организации.
